# Database foundation and university infrastructure

One workspace represents one university. Users are global; memberships associate
users with any number of workspaces. UUID primary keys are generated by the ORM.
Email and slug have global unique constraints (currently case-sensitive).
Memberships are unique by `(user_id, workspace_id)` and require an explicit role:
`owner`, `admin`, `member`, or `viewer`, enforced by a database check constraint.
Unique constraints provide indexes; an additional workspace index supports tenant
membership lookups. Deleting a user or workspace cascades to its memberships.
Timestamps are database-generated and timezone-aware in PostgreSQL.

Infrastructure now includes Campus, Building, Floor, RoomType, Room, Facility,
and RoomFacility. Every infrastructure table includes a required `workspace_id`.
Composite foreign keys pair that workspace with each referenced parent ID,
including both ends of RoomFacility. Cross-workspace associations are rejected by
the database on inserts and updates, including ORM relationship assignments.
The infrastructure API scopes reads and writes to the workspace in its route.
Authorization and PostgreSQL RLS are not implemented. A workspace identifier is
not proof of permission: callers can still select any workspace's route until
authentication and membership authorization are added. Foreign keys do not isolate reads.

## Infrastructure decisions

- Campus codes and room codes are unique across a workspace. Building codes are
  unique within a campus; floor numbers are unique within a building.
- RoomType and Facility names are unique within a workspace. These names and
  codes are case-sensitive; no types or facilities are seeded or hard-coded.
- Capacity is a required PostgreSQL integer with `CHECK (capacity > 0)`.
  Floor numbers allow zero and negative values for ground/basement levels.
- Required `(workspace_id, id)` unique constraints support composite foreign keys.
  Tenant-first unique indexes and additional parent indexes support scoped queries.
- RoomFacility has a `(room_id, facility_id)` primary key plus `workspace_id`.
  Create/delete RoomFacility objects through `facility_links` / `room_links`;
  `Room.facilities` and `Facility.rooms` are read-only relationship views.
- Supply `workspace_id` explicitly on infrastructure and association objects.
  Referenced workspaces must already be persisted. Parent relationships synchronize
  the parent ID only, so assigning a foreign university's parent cannot silently
  overwrite the record's workspace. Workspace-to-campus assignment sets ownership.
- Deleting referenced infrastructure or a workspace with infrastructure is blocked.
  Prefer `is_active` for retirement. Room/facility deletion cascades only to their
  association rows. No cascading deletion of the campus/building/floor hierarchy.

The previously validated revision is `0002_university_infrastructure`, following
`0001_initial_tenants`. Both were applied and verified in Supabase during earlier
phases. Phase 2B changes neither the database schema nor the migrations.

## Phase 3A academic scheduling data

The current head is `0003_academic_scheduling`, following the unchanged `0002`.
Migration 0003 was applied and validated before Phase 3B. Phase 3B does not change
models or migrations and does not access Supabase.

The models are Department, Faculty, Course, Section, and ScheduleEntry. Each has
an ORM-generated UUID primary key, required workspace ownership, a database-created
timezone-aware `created_at`, and `is_active` defaulting to true. Faculty represents
a teacher record independent of User or authentication.

- Department codes, course codes, and faculty emails are unique within a workspace.
  Section names are unique within their course. Uniqueness remains case-sensitive,
  including email, and inactive records retain their uniqueness constraints.
- Composite foreign keys pair `workspace_id` with every academic parent ID,
  including ScheduleEntry's room, section, and faculty. Corresponding
  `(workspace_id, id)` unique constraints support those references. ORM parent
  assignments do not overwrite explicit workspace ownership.
- Student counts are required PostgreSQL integers with `CHECK (student_count > 0)`.
  This phase does not compare enrollment with room capacity.
- ScheduleEntry represents actual class occupancy during `[starts_at, ends_at)`.
  Both endpoints are required `TIMESTAMP WITH TIME ZONE` values, with
  `CHECK (ends_at > starts_at)`. Callers should supply timezone-aware datetimes;
  PostgreSQL stores instants, not the original timezone identifier.
- Adjacent intervals are conceptually non-overlapping. Overlapping and duplicate
  occupancy entries are currently allowed: conflict detection, exclusion
  constraints, recurrence, reservations, and imports are intentionally deferred.
- Tenant-first indexes cover faculty/course department lookups and schedule
  lookups by workspace/start, room/start, section/start, and faculty/start.
  Unique indexes also support workspace and course/section lookups.
- Referenced departments, courses, faculty, sections, and rooms cannot be deleted.
  Inactive schedule entries still retain their references. There are no academic
  deletion cascades.

The schedule's faculty and section must share a workspace, but may belong to
different departments. The schema does not impose teaching-assignment rules.
Relationships connect Workspace to departments, Department to faculty/courses,
Course to sections, and Room/Section/Faculty to schedule entries.

Credential-free validation uses migrated SQLite databases and offline PostgreSQL
SQL generation. SQLite does not preserve PostgreSQL timezone semantics; the
tests verify timezone-aware column definitions and PostgreSQL DDL, not a live
PostgreSQL timestamp round trip. No private configuration is needed. The live
validator's academic inspection helper is tested on disposable connections;
the live validator itself is not run during Phase 3B.

## Phase 3B academic API

Base path: `/api/workspaces/{workspace_id}`. Resource paths are `departments`,
`faculty`, `courses`, `sections`, and `schedule-entries`. Each supports:

| Method | Path after base | Result |
| --- | --- | --- |
| POST | `/{resource}` | Create, 201 |
| GET | `/{resource}` | Paginated list, 200 |
| GET | `/{resource}/{id}` | Retrieve, 200 |
| PATCH | `/{resource}/{id}` | Partial update, 200 |
| POST | `/{resource}/{id}/deactivate` | Set `is_active=false`, 200 |

All operations use the shared workspace service, Pydantic contracts, and error
format described below. Reads, parent checks, and mutations are workspace-scoped.
Bodies reject ownership fields, unknown fields, empty PATCHes, and null values
for required fields. Missing or foreign-workspace resource IDs return 404;
missing or foreign-workspace parent references return 422. Duplicates return 409.
Student counts must be strict positive 32-bit integers. Faculty emails receive
basic syntax and length validation; case-sensitive database uniqueness is preserved.

Schedules require timezone-aware timestamps (ISO 8601 with `Z` or an offset).
Inputs are normalized to UTC before persistence; responses serialize UTC instants
with an offset, including after database reloads. SQLite strips timezone information,
so response conversion treats its stored UTC values as UTC. PostgreSQL returns
aware values directly. The API does not reinterpret times in the workspace timezone.

The effective interval must satisfy `ends_at > starts_at`, including one-sided
PATCHes merged with the stored endpoint. Invalid ranges return 422 and leave the
record unchanged. PostgreSQL row locking serializes partial updates to the same
entry during this validation. This is not conflict detection between entries.
Intervals remain `[starts_at, ends_at)`; adjacent, overlapping, and exact duplicate
schedule entries are all allowed in this phase.

Lists use `limit`/`offset` and include inactive records. Deactivation is idempotent,
does not cascade, and PATCH can reactivate records. Inactive parents remain valid
references. There are no hard-delete academic endpoints. Room capacity checks,
recurrence, imports, conflict detection, authentication, and RLS remain deferred.
API tests use isolated SQLite with private configuration and production-engine
access explicitly blocked. No live PostgreSQL connection is used for this phase.

## Infrastructure API

Base path: `/api/workspaces/{workspace_id}`. Resources: `campuses`, `buildings`,
`floors`, `room-types`, `facilities`, and `rooms`. Interactive contracts and all
request/response schemas are available at `/docs`.

| Method | Path after base | Behavior |
| --- | --- | --- |
| POST | `/{resource}` | Create; returns 201 with the resource |
| GET | `/{resource}` | List; returns 200 with an array |
| GET | `/{resource}/{id}` | Get one; returns 200 |
| PATCH | `/{resource}/{id}` | Partial update; returns 200 |
| POST | `/{resource}/{id}/deactivate` | Set `is_active=false`; campuses, buildings, floors, rooms only |
| GET | `/rooms/{room_id}/facilities` | List assigned facilities |
| POST | `/rooms/{room_id}/facilities/{facility_id}` | Assign; returns 201 with the association |
| DELETE | `/rooms/{room_id}/facilities/{facility_id}` | Remove association only; returns 204 |

Lists accept `limit` (default 100, maximum 200) and `offset` (default 0), ordered
by creation time and ID. They include active and inactive records. Deactivation
is idempotent and does not cascade to children; PATCH can reactivate a record.
Inactive infrastructure may still be referenced. Room types and facilities have
no active flag, so they have neither deactivation nor deletion endpoints.

PATCH requires at least one field. Only `address` and `description` accept null
to clear their values; other fields cannot be null. Name/code whitespace is
trimmed, blank strings are rejected, and uniqueness remains case-sensitive.
Room capacity is a strict positive integer in PostgreSQL's 32-bit integer range.
Room facility assignment is separate from room create/update: repeating an
assignment returns 409, and removing a missing assignment returns 404.

Workspace ownership comes exclusively from the route. Request bodies reject
`workspace_id`, `id`, `created_at`, and other undeclared fields. Parent references
are validated in that workspace; database constraints protect against races.
All lookups and UPDATE/DELETE statements include workspace predicates. Responses
are Pydantic schemas, without ORM relationships or database diagnostics.

Errors share `{"detail": {"code": "...", "message": "..."}}`:

- 404: missing workspace, resource, or assignment. Foreign-workspace resources
  are indistinguishable from missing resources.
- 422: invalid request fields or a parent missing from the selected workspace.
- 409: duplicate code/name/floor number/assignment, or a concurrent integrity conflict.
- 503: database failure, with SQL and connection diagnostics suppressed.

The code is separated into `routes.py`, `schemas.py`, `services.py`, and
`errors.py`; `main.py` composes these and preserves `/health`.

## Database configuration

Supabase-hosted PostgreSQL is the primary development database. Local PostgreSQL
is not required. The backend continues to use SQLAlchemy, psycopg, Alembic, and
pydantic-settings; no Supabase client SDK is needed.

If absent, copy `.env.example` to `.env` in this directory. Edit only your local
`backend/.env`, which Git ignores:

```dotenv
DATABASE_URL=postgresql+psycopg://USER:PASSWORD@DATABASE_HOST:5432/DATABASE_NAME?sslmode=require
```

Use your private Supabase PostgreSQL connection details for the username,
password, host, port, and database, retaining the `postgresql+psycopg` driver.
The values above are placeholders only; preserve an already configured `.env`.
Percent-encode special characters in the username/password URL
components (for example, `@` becomes `%40`). Do not share the URL or put real
credentials in `.env.example`. Process environment variables override `.env`.
Settings resolve `.env` relative to the backend directory, independent of cwd.
Placeholder or missing credentials are rejected when database access is requested.

For initial database setup only, from `backend/` in PowerShell (the existing
Supabase development database is already migrated; API tests do not run this):

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic check
```

The initial revision is `0001_initial_tenants`. No tables are created at API
startup. Database access is lazy; FastAPI endpoints inject a session
with `Depends(get_session)` from `app.database`. Each dependency owns and closes
its session; writes require explicit commits and uncommitted work is rolled back.
`/health` remains a process health endpoint.

## Credential-free checks

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-test.lock
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m compileall -q app alembic tests
.\.venv\Scripts\python.exe -m alembic upgrade head --sql
```

Tests use temporary SQLite databases for constraints, relationships, and migration
round trips, plus offline PostgreSQL SQL generation and configuration checks with
fake credentials. They never connect to your PostgreSQL database. SQLite tests do
not replace validating the migration against the configured Supabase PostgreSQL database.
API tests override the session dependency with an in-memory SQLite database and
block production engine/configuration access. No test reads the private `.env`
or connects to Supabase. `requirements-test.lock` extends the runtime lock with
the test client dependency; runtime dependencies are unchanged.

For a read-only live schema validation (including `alembic check`), run:

```powershell
.\.venv\Scripts\python.exe scripts/validate_database.py
```

This loads the connection privately through the application configuration and
prints only validation outcomes. It neither changes schema nor writes user data.

Implementation references: [SQLAlchemy sessions](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)
and [Alembic migrations](https://alembic.sqlalchemy.org/en/latest/tutorial.html).
Tenant-aware relationship synchronization follows SQLAlchemy's
[overlapping foreign key guidance](https://docs.sqlalchemy.org/en/20/orm/join_conditions.html#overlapping-foreign-keys).
API tests follow [FastAPI dependency overrides](https://fastapi.tiangolo.com/advanced/testing-dependencies/)
and use the client dependency described in [Starlette testing documentation](https://starlette.dev/testclient/).
