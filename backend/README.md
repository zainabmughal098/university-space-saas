# Initial database foundation

One workspace represents one university. Users are global; memberships associate
users with any number of workspaces. UUID primary keys are generated by the ORM.
Email and slug have global unique constraints (currently case-sensitive).
Memberships are unique by `(user_id, workspace_id)` and require an explicit role:
`owner`, `admin`, `member`, or `viewer`, enforced by a database check constraint.
Unique constraints provide indexes; an additional workspace index supports tenant
membership lookups. Deleting a user or workspace cascades to its memberships.
Timestamps are database-generated and timezone-aware in PostgreSQL.

This establishes tenant associations only. Authorization and PostgreSQL RLS are
not implemented. Future tenant-owned tables should reference `workspace_id`, and
future queries must be scoped to the authorized workspace.

## Database configuration

Supabase-hosted PostgreSQL is the primary development database. Local PostgreSQL
is not required. The backend continues to use SQLAlchemy, psycopg, Alembic, and
pydantic-settings; no Supabase client SDK is needed.

If absent, copy `.env.example` to `.env` in this directory. Edit only your local
`backend/.env`, which Git ignores:

```dotenv
DATABASE_URL=postgresql+psycopg://USER:PASSWORD@DATABASE_HOST:5432/DATABASE_NAME?sslmode=require
```

Use your private Supabase PostgreSQL connection details for the username,
password, host, port, and database, retaining the `postgresql+psycopg` driver.
The values above are placeholders only; preserve an already configured `.env`.
Percent-encode special characters in the username/password URL
components (for example, `@` becomes `%40`). Do not share the URL or put real
credentials in `.env.example`. Process environment variables override `.env`.
Settings resolve `.env` relative to the backend directory, independent of cwd.
Placeholder or missing credentials are rejected when database access is requested.

From `backend/` in PowerShell, after setting credentials:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic check
```

The initial revision is `0001_initial_tenants`. No tables are created at API
startup. Database access is lazy; future FastAPI endpoints can inject a session
with `Depends(get_session)` from `app.database`. Each dependency owns and closes
its session; writes require explicit commits and uncommitted work is rolled back.
`/health` remains a process health endpoint.

## Credential-free checks

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m compileall -q app alembic tests
.\.venv\Scripts\python.exe -m alembic upgrade head --sql
```

Tests use temporary SQLite databases for constraints, relationships, and migration
round trips, plus offline PostgreSQL SQL generation and configuration checks with
fake credentials. They never connect to your PostgreSQL database. SQLite tests do
not replace validating the migration against the configured Supabase PostgreSQL database.

For a read-only live schema validation (including `alembic check`), run:

```powershell
.\.venv\Scripts\python.exe scripts/validate_database.py
```

This loads the connection privately through the application configuration and
prints only validation outcomes. It neither changes schema nor writes user data.

Implementation references: [SQLAlchemy sessions](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)
and [Alembic migrations](https://alembic.sqlalchemy.org/en/latest/tutorial.html).
